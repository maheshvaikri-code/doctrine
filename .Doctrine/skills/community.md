# Skill: Community

**Scope.** The owned audience — forum, chat server, issue threads, user
group: the surface where users talk to you and to each other. Every
outbound post, reply, and comment is a draft; the human sends.

## Principles
- A community is a product surface with a maintenance cost, not a free
  channel. Unstaffed it does not go quiet — it fills with unanswered
  questions and becomes the product's most visible review.
- An audience receives; a community talks to itself. The test is whether
  members answer each other, and whether they would still show up if you
  stopped posting.
- Show up before you need something. A first post that is an ask is the
  reason the second post gets no replies.
- Answer in public so the answer compounds: a DM helps one person once, a
  thread helps everyone who searches it afterwards.
- Advocates are earned by shipped fixes, never bought. Someone who
  watched their bug close defends you; someone handed swag does not.

## Defaults
- A code of conduct exists as a written artifact with a named enforcer
  and a stated process before the space opens. Rules nobody enforces
  teach members that the rules are decoration.
- Recurring-question rule: asked twice it becomes a docs entry, asked a
  fourth time it is a product or UX defect routed through intake
  (`skills/customer-support.md`), never a fifth hand-typed answer.
- The response commitment is stated and small — what maintainers answer,
  what they do not, how long a thread waits — because a promise nobody
  audits decays into a lie.
- Moderation actions are logged with the rule cited and the member
  notified; the same rule lands the same way whoever broke it.
- Posts, replies, comments, and DMs are drafts queued for the human
  (.Doctrine.md §5). The skill writes the words and never the send.

## Do
- Answer in the thread the question was asked in, then link the docs page
  that answer just earned.
- Bridge patterns into the gates rather than answering the same thread
  a third time: `roles/support-engineer.md` owns the intake rule and the
  threshold (`skills/customer-support.md`).
- Close the loop in public when the fix ships — name the version, credit
  the reporter as they prefer, let the thread stand as the receipt.
- Wind a community down honestly when it can no longer be staffed:
  announce a date, archive read-only, point to where talk moved. A dead
  server nobody closed reads as a dead product.

## Don't
- Don't report member count as health; answered-question rate and
  member-to-member replies are the numbers that pay rent
  (`skills/metrics.md`).
- Don't answer the loud thread and skip the quiet one — triage by user
  impact, the same as any other intake queue.
- Don't moderate by mood: a rule enforced against a critic and waived for
  a fan has stopped being a rule.
- Don't use the community as the support queue's overflow drain; pain
  posted in a channel is still a ticket.
- Don't post, reply, comment, or DM anything yourself — every word goes
  to the human to send.

## Review checklist
- [ ] Code of conduct written, enforcer named, process stated
- [ ] Recurring questions promoted to docs or filed as defects
- [ ] Answers given in public; the thread links the docs it produced
- [ ] Moderation logged with the rule cited and the member notified
- [ ] Health read as answers and member replies, not headcount
- [ ] Every outbound post, reply, and DM queued as a draft for the human

## Common failure modes
The launch-day server nobody staffed by week three; a first post that is
an ask; one maintainer answering the same question forty times and never
writing the page; moderation strict with critics and lenient with fans
until the rules read as favoritism; member count climbing on a dashboard
while the answered-question rate falls; a community left rotting in
public because closing it honestly felt like an admission.
